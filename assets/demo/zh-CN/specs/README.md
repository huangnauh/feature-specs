# 功能规格工作流

将 `specs/` 作为已跟踪功能的需求、动态设计、交付进度和验证入口。除非项目另有稳定约定，
功能目录命名为 `YYYYMMDD-feature-name`。

## 只创建工作所需的文档

| 场景 | `spec.md` | `design.md` | `plan.md` |
| --- | --- | --- | --- |
| 明确的一次性局部变更 | 可选 | 可选 | 可选 |
| 不跟踪的有界探索 | 可选 | 必需 | 不创建 |
| 跨会话跟踪的功能 | 必需 | 按不确定性需要 | 按交付复杂度需要 |
| 多切片交付 | 必需 | 已验证，或说明为何不需要 | 必需 |

如果存在 `plan.md`，则必须存在 `spec.md`。不要创建空的评审、探索或产物目录。

## 事实源职责

- `spec.md`：可观察结果、目标、约束、非目标、验收、功能状态、优先级、负责人、依赖和阻塞项。
- `design.md`：证据、不变量、假设、开放问题、候选契约、方案、替代方案、失败语义、兼容性和设计增量。
- `plan.md`：交付切片、依赖顺序、当前进度、已执行验证、回滚和剩余交付风险。
- `explorations/*.md`：一次有界探索的可追溯过程证据；不是当前设计或交付状态的事实源。

需求变更写入 `spec.md`，技术变更写入 `design.md`，实施进度写入 `plan.md`。文档之间应相互链接，
不要复制结论。

只有局部、单切片且不需要跨会话推进的已跟踪功能，才可以在没有计划时由规格记录完成证据。
多切片、跨会话或保留原型后继续扩展的交付必须创建计划。

不要新增另一个重复当前计划状态的任务看板。

## 证据语言

仅在区分会改变技术判断时使用以下标签：

- `Observed`：已直接证明且有明确证据范围的事实。
- `Hypothesis`：可证伪的候选判断。
- `Open`：缺失信息导致无法安全决策。
- `Decision`：经评审并针对明确范围接受的结论。

设计验证和 ADR 接受只提升其明确覆盖的范围。验证记录使用 `Executed`、`Static evidence`、
`Not executed` 和 `Residual risk`。不得把建议执行的命令报告为已执行。

开始探索前先分类未知项：

- `Requirement decision`：会实质改变结果、范围或验收的未决用户/产品选择；只有尚未由用户、
  已接受需求或 ADR 授权或决定时才需要确认，不能由实现代替。
- `Contract evidence gap`：先审计权威 source contract、直接调用链、测试、schema 或运行事实，
  或在编写依赖它的生产逻辑前执行最小有界 probe。
- `Technical hypothesis`：用可证伪的有界实验验证。
- `Implementation concern`：方向不变，在计划下 `Code -> Verify`，不创建探索。

## 工作流

### 设计优先

```text
想法 -> 需要跟踪时创建 Spec + 设计草案
     -> 可选探索 -> 修订 / 验证设计
     -> 计划 -> 生产实现 -> 验证
```

### 原型优先

```text
想法 -> 有界探索 -> 回顾性设计 -> 评审
     -> keep / rework / discard
     -> 验证设计 -> 计划 -> 生产实现 -> 验证
```

探索代码或保留的原型不会自动成为生产实现。

## 状态

功能：

- `Exploring`：仍存在实质性未知项。
- `Shaping`：结果、范围或验收条件仍在收敛。
- `Ready`：需求稳定且已满足实施前置条件。
- `Implementing`：至少一个交付切片正在进行。
- `Verifying`：实现已存在，但要求的验证尚未完成。
- `Blocked`：已明确的外部事实、依赖、环境或授权阻止继续推进。
- `Completed`：验收、验证、文档和状态回写均已完成。
- `Superseded`：已由明确指定的后继功能取代。

设计：

- `Exploring | Proposed | Validated | Superseded`

计划：

- `Draft | Ready | In Progress | Verifying | Blocked | Replan Required | Completed`

当证据推翻关键假设，或实施会改变已接受的契约时，将计划设为 `Replan Required`。
继续实施前先更新设计。

## 有界探索

仅当探索具有风险、跨模块、可丢弃、需要比较不同方案，或其过程细节会淹没动态设计时，
才创建探索文档。

记录：

1. 问题、假设和证伪条件；
2. 不变量、范围和停止条件；
3. 环境、实际源码/worktree 状态、相关改动范围以及可复现动作；
4. 有意义的尝试、失败和被迫调整；
5. 已执行、静态和未执行的证据，以及剩余风险；
6. 假设结果和实现处置；
7. 设计影响和明确的退出决定。

假设结果使用 `Supported | Revised | Rejected | Inconclusive`。原型处置单独使用
`keep | rework | discard`。

### 探索退出与交付提升

- 问题或证伪条件被回答时立即结束探索，记录结果、处置、设计影响和明确的退出决定，例如
  停止、将保留工作提升到 design 和 plan，或进行一个不同的下一实验；除非项目工具要求，
  不使用固定字面量。
- `keep` 不会自动把原型提升为生产实现。跨会话或多切片扩展前，必须让对应 delivery design
  达到 `Validated` 并创建 plan；否则拆分、返工或停止。
- 代表性契约模式成立后，不为同类 operation、页面或 adapter 连续创建探索；只有出现新的
  事实源、trust boundary、协议形态或 failure model 时才做不同的下一实验。
- 不在已结束探索或 design delta 中追加普通交付进度。
- dirty worktree 是 code-bearing 探索的正常执行状态。如实记录能取得的 base ref、
  `clean | dirty` 和相关改动范围；只有强复现会改变技术判断或支持声明时，才保存
  diff/artifact identity。后续 commit 只能标为保留结果，不能倒填成历史执行快照。

## 项目定义的辅助文档

项目或功能可在具体问题确有需要时新增辅助文档。应在本地定义该文档的职责和权威事实源。
不要把一次性产物当作跨项目约定、加入核心模板集，或让其重复功能状态。

能力矩阵等辅助文档可以成为逐项映射和交付状态的唯一事实源。此时计划只维护批次、
delivery stage 和 gate，规格不复制逐项计数，设计只记录新出现或被证伪的契约模式，
探索不累计后继交付进度。

## 完成边界

切片应按可观察结果和证据门槛完成，而不是按文件、类型、接口或抽象的创建完成。
完成、兼容和支持声明不得超出实际证据覆盖范围。
